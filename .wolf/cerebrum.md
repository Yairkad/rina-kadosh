## Do-Not-Repeat

- **[2026-08-20] אסור לפרוס קוד שמוסיף עמודת DB חדשה לשאילתת SELECT בעמוד ציבורי לפני שהמיגרציה רצה בפועל** — אם ה-`.select("...")` כולל עמודה שלא קיימת עדיין ב-DB, השאילתה נכשלת לגמרי (`42703`) וזה שובר את כל העמוד בפרודקשן, לא רק "לא מציג את השדה החדש". סדר נכון: (1) לכתוב את קובץ המיגרציה, (2) לבקש מהמשתמש להריץ אותו ידנית ב-SQL Editor (אין גישת DB-write בסשן הזה — לא Supabase MCP מאומת ולא CLI מקושר), (3) **לאמת בפועל** מול ה-REST API שהעמודה קיימת (curl עם anon key מספיק, `column ... does not exist` = עדיין לא רץ), **ורק אז** לעשות commit+push. נעשה נכון פעם אחת (background_image, 2026-08-19) — לשמור על אותו סדר בכל פעם שמוסיפים עמודה.

- **[2026-08-19] נסיון proxy route (`/api/media`) לעקוף חסימת Netfree על וידאו מ-supabase.co — נכשל ונמחק, אל תבנה מחדש** — הרעיון: להעביר את קובץ הווידאו של `atmosphere_image` דרך API route באתר עצמו (same-origin) במקום קישור ישיר ל-Supabase Storage, כי נטפרי (ומסנני תוכן ישראליים דומים) חוסמים לפי סיווג domain, ו-`*.supabase.co` הוא domain משותף שעלול להיות מסווג בעייתי. **בבדיקה מקומית:** ה-proxy עצמו נכשל עם 418 מ-Cloudflare (כנראה חסימת בוט לפי TLS fingerprint, לא הדרים) — נבדק גם ב-edge runtime וגם ב-node, שניהם נכשלו באותה צורה. **בפרודקשן (אחרי push):** המשתמש דיווח "ככה לא עובד בכלל" — כלומר הבעיה לא הייתה ספציפית לסביבת הפיתוח המקומית, ה-proxy לא עבד גם שם. **הפתרון בפועל שהמשתמש מצא: לא קוד בכלל** — פנה לנטפרי וביקש אישור/הסרת חסימה ידנית לקישור הספציפי מ-Supabase, וזה עבד. **מסקנה: אם עולה שוב בעיית Netfree/מסנן תוכן על נכס מדיה מ-Supabase Storage — הפתרון המהיר והאמין הוא לבקש מהמשתמש לפנות ישירות לנטפרי (יש להם מנגנון בקשת אישור אתר/קישור), לא לנסות שוב proxy route בצד השרת — זה נכשל פעם אחת כבר בשתי סביבות שונות (dev + prod) מאותה סיבה (חסימת בוט של Cloudflare על הבקשה השרת-לשרת, לא קשור להדרים שנשלחים).** קוד ה-proxy (`app/api/media/[...path]/route.ts`, `lib/utils.ts::toProxiedMediaUrl`) הוסר לגמרי מהקוד ב-commit שאחרי.
